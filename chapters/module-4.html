01 / The development process

Let the evidence choose the next fix.

Start with a rough, complete workflow. Inspect a small set of outputs—roughly 10–20 is enough to start finding recurring problems. Turn an important weakness into an evaluation you can rerun.

Prototype → inspect → evaluate → diagnose → improve → rerun.

Do not spend all your effort tuning the easiest component to edit. Find the component that is responsible for important observed failures. As the system matures, add more representative cases and more focused component tests.

Pause & reason

You changed a prompt and the answer looks better. What is the next step?

Reveal the reasoning

Rerun the same evaluation cases. Inspect regressions and whether the metric captures the improvement you care about. A single attractive example is weak evidence.

02 / Context & components

Keep the evaluation system visible.

The product produces an answer. The evaluator scores that answer. The error ledger records diagnosis from traces. These responsibilities should remain distinct so changing a scorer does not quietly change the product’s behavior.

03 / Four kinds of eval

Choose the evidence and the scorer.

The course uses two independent dimensions: whether expected evidence is specific to each example or shared across examples, and whether code or a model evaluates it.

Expected evidenceObjective code checkSubjective model judgment
Per-example ground truthInvoice due date equals the labeled dateReport covers the topic’s expert-provided talking points
One shared rule / rubricCaption has at most 10 wordsChart satisfies title, labels, type, and range criteria

Make a metric concrete

Python · small objective scorers
def exact_date(extracted, expected):
    return extracted == expected  # Both normalized to YYYY-MM-DD.

def short_caption(text):
    return len(text.split()) <= 10

A date check must define formatting and how invalid outputs are scored. The word counter uses whitespace-separated tokens as its explicit counting convention. For a model judge, request named criterion scores plus an explanation, then validate the returned structure.

Do not confuse a valid score with a meaningful metric. A report may contain preferred URLs while failing to answer the user’s question. A judge can return well-formed JSON and still make poor judgments.

Pause & reason

Is “ground truth” always an exact answer string?

Reveal the reasoning

No. In the course’s research example it can be a list of gold-standard discussion points, whose coverage is assessed by a model judge.

04 / Error analysis

Read the trace, then label the failure.

Suppose a research report misses a high-profile development. Inspect the generated search terms, returned search results, selected sources, and reasoning over fetched text. Each stage can introduce a different defect.

StageQuestion to askPossible diagnosis
Query generationAre terms specific and relevant?Weak search terms
Search resultsWere appropriate sources surfaced?Poor retrieval
Source selectionDid the workflow choose useful pages?Bad ranking or selection
WritingDid it use the retrieved evidence?Omission or reasoning failure

Invoice traces similarly distinguish missing text during PDF extraction from selecting the wrong date later. Email traces separate incorrect query construction, bad database records, and an unhelpful draft.

One failed run can have several defects

The course’s invoice and email ledgers allow overlapping labels. Decide whether your analysis records the first failure, a primary cause, or every observed defective component.

Failed casePDF-to-text defectDate-selection defect
Invoice ANoYes
Invoice BYesYes
Invoice CNoYes

Date selection appears in 3/3 failed cases; PDF-to-text in 1/3. Their percentages sum to more than 100% because labels overlap. The denominator is failed cases, not all requests.

Python · multi-label failure rates
def label_rates(failed_ledger):
    counts = Counter(label for row in failed_ledger for label in set(row["labels"]))
    n = len(failed_ledger)
    return {label: count / n for label, count in counts.items()} if n else {}

Frequency informs prioritization; consider the importance of each failure too. A rare consequential defect can deserve attention before a common cosmetic defect.

05 / Component experiments

Isolate the component you are changing.

Rerunning an entire search → draft → reflection system after a small search change costs time and can bury the effect under variation from later steps. A component evaluation measures the changed step more directly.

The slides suggest checking returned web resources against a preferred list and tracking the metric as you change provider, result count, or date range. Here is a small illustrative ratio:

Python · requires urllib.parse.urlsplit
def preferred_ratio(urls, domains):
    if not urls:
        return 0.0
    # Exact host comparison, not substring matching in a URL.
    return sum(urlsplit(url).hostname in domains for url in urls) / len(urls)

Two preferred hosts among five returned URLs give 2/5 = 0.4. Define empty results explicitly; this exercise scores them as zero. Exact host matching avoids accepting example.org.evil.test as example.org.

Source boundary: a Module 4 notebook is not present in this repository. This function is a teaching implementation of the slide’s component-evaluation idea, not an attributed course-lab function.

The ratio is a proxy for one source property. It does not establish recall, factuality, freshness, or answer coverage. Once the component improves, rerun the end-to-end evaluation to check whether user-facing quality also improved.

Component typeInterventions from the course
Non-LLMTune parameters or replace the service: search count/date range, retrieval threshold/chunk size, model detection threshold
LLMClarify instructions, add examples, compare models, split the step, or consider fine-tuning after simpler interventions

Build intuition by trying models on a personal test set and reading effective prompts. Use measured results to choose the application configuration.

06 / Runnable evaluation

Run an evaluation you can audit.

Python · a fixture evaluation harness
def evaluate(cases, outputs):
    if not cases:
        raise ValueError("evaluation requires cases")
    runs = [{"id": case["id"], "expected": case["expected"],
             "actual": outputs[case["id"]],
             "pass": outputs[case["id"]] == case["expected"]} for case in cases]
    return {"accuracy": sum(r["pass"] for r in runs) / len(runs), "runs": runs}

This fixture compares four labeled date outputs across two versions. The revised output map fixes two cases, so accuracy moves from 1/4 to 3/4. That is a controlled example of aggregation, not evidence about a real model.

Runnable teaching extension · standard library only · deterministic fixtures, no model or external service calls.

07 / Latency, cost & pitfalls

Optimize the expensive part you measured.

The course puts useful output quality first, then latency, and cost when scale makes it important. Know your application’s budgets early, but avoid tuning speed for a workflow that cannot do the task.

MeasureInspectPossible change
LatencyDuration of every span and the dependency pathParallelize independent work; compare a faster model
CostTokens, API calls, and compute per stepReduce repeated work; compare a cheaper component
QualityEnd-to-end and component resultsKeep constraints satisfied after optimization

If three independent searches take two seconds each, their ideal parallel contribution is about two seconds rather than six, before orchestration overhead. Dependent steps cannot be combined this way: a draft still needs the retrieved evidence.

Evaluation failureRemedy
Metric blindnessImprove the metric using observed misses
Noisy end-to-end signalAdd a focused component evaluation
Judge inconsistencyUse explicit criteria and check calibration
Unrepresentative easy setAdd realistic and failing cases
Component improves but product worsensRecheck the end-to-end result

08 / Recall & checklist

Defend your next engineering decision.

Answer before opening the explanation. Then revisit the example that exposed a gap.

Why begin with 10–20 examples?

To find an initial useful signal quickly. Grow the set as failure coverage and reliability requirements increase.

Why can a component eval be clearer and cheaper?

It isolates the changed step and avoids executing unrelated stochastic stages.

When should latency and cost become the main optimization target?

When quality meets the application’s needs and measured latency or usage cost is a meaningful constraint.

Why can error percentages exceed 100%?

One failed case can have multiple defect labels; state the denominator and labeling policy.

Does a preferred-source ratio establish report quality?

No. It measures one retrieval property. Confirm downstream answer quality separately.
