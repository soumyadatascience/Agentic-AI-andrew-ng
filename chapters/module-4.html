Evaluation defines what better means

An evaluation pairs representative tasks with a way to judge outcomes. It lets a team compare versions, detect regressions, and decide whether a change improved the behavior that matters.

01

Representative cases

Include the common path, difficult examples, and failures that matter.

02

Clear criteria

State what correctness, quality, safety, and completion mean for the task.

03

Repeatable runs

Use the same cases and scoring approach when comparing versions.

04

Useful slices

Break aggregate scores down by task type or failure category.

General context: checks can be deterministic when the answer is objectively testable, model-based when structured judgment is needed, and human when nuance or stakes demand it.

Practical discipline: change one important thing at a time when possible, so the next evaluation can tell you what caused the difference.

Error analysis turns failures into a prioritized worklist

An aggregate score says whether performance changed. Error analysis asks why. Inspect failed traces and outputs, group recurring failure modes, estimate their frequency and impact, then choose the problem with the best expected payoff.

  1. Collect
    Keep the evidence. Save inputs, intermediate decisions, tool calls, outputs, and evaluation results.
  2. Group
    Label recurring failure modes. Examples might include missing context, wrong tool selection, bad arguments, weak synthesis, or an incorrect stopping decision.
  3. Rank
    Prioritize by frequency and consequence. A rare severe error may outrank a frequent cosmetic issue.
  4. Fix
    Address the responsible layer. Improve data, prompts, tools, routing, checks, or system structure according to the diagnosis.

Do not optimize the component that is easiest to edit; optimize the failure that the evidence identifies.

Component-level evaluations reveal where the system breaks

End-to-end evaluation reflects the user experience, but it can hide the source of failure. Component checks isolate the decisions that compose the workflow.

01Input + retrievalWas the needed context found and passed forward?
02Planning + routingWas the right next step or tool selected?
03ExecutionWere arguments valid and actions completed correctly?
04Synthesis + stoppingWas the final result faithful, complete, and properly concluded?

A useful development process keeps both views: end-to-end checks protect the overall outcome, while component-level checks make diagnosis and targeted improvement faster.

Quality, latency, and cost belong on the same scorecard

More model calls, more tools, and more retries can improve some outcomes while making the workflow slower and more expensive. Practical development measures these tradeoffs rather than assuming the most elaborate workflow is best.

QualityDid the workflow produce the desired result?Track correctness, completeness, robustness, and safety.
LatencyHow long did the user or downstream process wait?Inspect slow components, serial dependencies, and unnecessary retries.
CostWhat resources did the result consume?Measure model usage, tool calls, and repeated work per successful task.
Optimization question: what is the simplest workflow that reaches the required quality at an acceptable latency and cost?

Self-check

Why is an aggregate evaluation score not enough?

It shows overall change but can hide which task types failed and which component caused the failures. Slices and error analysis make the result actionable.

How do end-to-end and component-level evaluations differ?

End-to-end evaluations judge the overall user-facing outcome; component evaluations isolate particular steps such as retrieval, routing, tool execution, or synthesis.

When is a more complex agentic workflow not an improvement?

When its quality gain does not justify added latency, cost, fragility, or operational risk for the task’s requirements.
