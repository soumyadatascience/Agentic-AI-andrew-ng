01 / What planning changes

A plan is an artifact before it is an action.

In a fixed workflow, application code decides the route before the request arrives. In a planning workflow, the model proposes a route for the current goal using descriptions of the available capabilities.

Request → proposed plan → execution → observed result.

Consider “Do you have any round sunglasses under $100 in stock?” The plan needs to find matching products, check availability, apply the price ceiling, and answer from the records. A return needs a different sequence: identify the purchase, inspect the item, and apply the return policy.

The course’s email example similarly composes search, reply, and archive for a particular request. Planning changes which steps are selected or ordered; application code still executes them.

This is an architectural view. In the local demonstration, TinyDB tables live in the notebook environment; an external store service is a deployment choice shown here to clarify ownership, not a claim about the notebook’s deployment.

02 / Plans as data and code

Make the plan’s data dependencies explicit.

The course first shows plans as steps in text, then as JSON. Structured plans expose tool names, arguments, and references to prior results. The application must resolve those references before dispatch.

JSON · teaching plan, not a tool API schema
{
  "plan": [
    {"step": 1, "tool": "get_item_descriptions",
     "args": {"query": "round sunglasses"}},
    {"step": 2, "tool": "check_inventory",
     "args": {"items_from_step": 1}},
    {"step": 3, "tool": "get_item_price",
     "args": {"items_from_step": 2}}
  ]
}

The reference field items_from_step is an explanatory convention. It is not a magical variable and is not shown as a verbatim course API. A runner reads the stored result of that step, validates it, and constructs the next call. The final answer also needs to enforce the requested price constraint.

Why express a plan as code?

A long menu of narrow data tools can become brittle: filter each month, compute each aggregate, repeat, then compare. Python can express filtering, grouping, and sorting in a compact program. The course shows code for recent transactions and unique transactions as examples.

Plan envelope · intentionally incomplete illustration
<execute_python>
# Plan: read the data, filter the request, compute the answer.
# The application must provide a suitable execution environment.
answer_text = "..."
</execute_python>

Code is more expressive, so the execution boundary matters more. Extracting tags makes the program inspectable; it does not make the program safe.

Pause & reason

A plan says “results from step 1.” What must the runner do?

Reveal the reasoning

Resolve a real stored artifact, validate the expected shape, and pass concrete arguments. Natural-language references do not bind themselves to tool inputs.

03 / Execution & authority

Separate the lab from the guarantees you need.

The notebook’s generate_llm_code constructs the proposal. execute_generated_code extracts the program and executes it. customer_service_agent orchestrates generation, before/after inspection, and result packaging.

BoundaryWhat the notebook implementsWhat it does not establish
GenerationPrompt asks for request-derived constraints and policiesIndependent enforcement of those policies
Executionexec with supplied globals and locals; exception captureA secure sandbox or a separate plan validator
Business writesGenerated code can reach table objectsRollback or concurrency control
ResultsCode, stdout, error, answer, table snapshotsGuaranteed truthful answer or a validated status field

Important correction: a dictionary named SAFE_GLOBALS is not a security boundary. The inspected executor does not supply a standalone validate_plan function. Its prompt requests disciplined behavior; application enforcement is a separate engineering responsibility.

The prompt asks generated code to set answer_text and STATUS. The concrete executor returns an answer field and captured output; it does not return a separately validated status field. Inspect the actual result contract instead of inferring it from prompt wording.

Notebook contracts · condensed, not copy-and-run code

    → full model response

execute_generated_code(content, db=..., inventory_tbl=...,
                       transactions_tbl=..., user_request=...)
    → code, stdout, error, answer, inventory_tbl, transactions_tbl

customer_service_agent(question, ..., reseed=False)
    → full_content, exec

04 / The purchase trace

Trace a two-item purchase.

The local customer-service example asks to buy three Classic sunglasses and one Aviator. The following trace uses the lab’s example quantities and prices with an opening balance of $500.

StageArtifact / transitionEffect
RequestClassic × 3; Aviator × 1None
ObserveClassic: 10 at $60; Aviator: 23 at $80Read
Validate3 ≤ 10 and 1 ≤ 23No write yet
Classic purchaseStock 10 → 7; line total $180; balance $500 → $680Inventory + transaction row
Aviator purchaseStock 23 → 22; line total $80; balance $680 → $760Inventory + transaction row
PackageAnswer, output logs, error, and tablesEvidence retained

Each line has its own transaction record and a sequential running balance. Checking every requested item before the first write prevents a predictable stock failure from being discovered after an earlier item was already changed.

The requested behavior envelope

ConditionIntended behavior
Ambiguous actionRead-only dry run
No matching productno_match; offer a relevant next step
Insufficient stockinsufficient_stock; do not write
Unparseable quantityinvalid_request
Unsupported actionunsupported_intent
Successful supported actionsuccess; short answer plus evidence

These are requested policies for generated code. They are not unconditional guarantees of the original executor. The course also demonstrates returning two Aviator glasses, increasing stock from 23 to 25, and adjusting the transaction balance.

reseed=True resets demonstration inventory and transactions for a reproducible run. It is a test setup choice, not a customer action. With reseeding off, later calls continue from prior state.

Pause & reason

Both items passed stock validation. Does that prevent a partial write if the second insert fails?

Reveal the reasoning

No. Pre-validation handles predictable invalid inputs. Atomic execution or an explicit recovery design is needed for failures during writes.

05 / Runnable state exercise

Put state changes behind bounded code.

For the teaching extension, the model’s proposed purchase is a list of product/quantity pairs. Application code validates that list, calculates updates on a candidate state, and commits only after the whole operation succeeds.

The exercise also remembers a request ID. Repeating the same purchase returns already_applied; reusing the ID for different quantities returns id_conflict. This makes retry behavior explicit.

Python · bounded in-memory purchase operation
def purchase(state, request_id, lines, fail_after=None):
    if not isinstance(request_id, str) or not request_id:
        return {"status": "invalid_request"}
    if not isinstance(lines, list) or not lines:
        return {"status": "invalid_request"}
    quantities = {}
    for line in lines:
        if not isinstance(line, dict) or set(line) != {"product", "qty"}:
            return {"status": "invalid_request"}
        name, qty = line["product"], line["qty"]
        if not isinstance(name, str) or name not in PRICES or type(qty) is not int or qty <= 0:
            return {"status": "invalid_request"}
        quantities[name] = quantities.get(name, 0) + qty
    fingerprint = tuple(sorted(quantities.items()))
    if request_id in state["receipts"]:
        prior = state["receipts"][request_id]
        return {"status": "already_applied" if prior == fingerprint else "id_conflict"}
    if any(qty > state["stock"][name] for name, qty in quantities.items()):
        return {"status": "insufficient_stock"}
    candidate = deepcopy(state)
    for index, (name, qty) in enumerate(quantities.items(), 1):
        candidate["stock"][name] -= qty
        candidate["balance"] += PRICES[name] * qty
        candidate["transactions"].append({"product": name, "qty": qty,
                                           "balance": candidate["balance"]})
        if index == fail_after:
            return {"status": "execution_failed"}  # Original state unchanged.
    candidate["receipts"][request_id] = fingerprint
    state.update(candidate)  # One commit in this single-threaded fixture.
    return {"status": "success"}

This is a single-process, single-threaded in-memory exercise. Its staged update illustrates a commit boundary; it is not a durable transaction system, concurrency-safe inventory service, or sandbox. Those require additional engineering.

Runnable teaching extension · standard library only · deterministic fixtures, no model or external service calls.

  2. Use fail_after=1. Verify that the original state is unchanged.

06 / The multi-agent pipeline

A team is a set of explicit handoffs.

The market-research notebook uses a fixed Python pipeline with four specialized roles. Each function receives a concrete artifact and returns another. The pipeline does not rely on an invisible shared conversation.

The designer returns {image_path, prompt, caption}. The copywriter returns a quote and justification. The packaging function reads the summary, image path, quote, and justification, then writes a Markdown report.

Python-like sketch · fixed artifact handoffs
research = market_research_agent()
visual = graphic_designer_agent(research)
copy = copywriter_agent(visual["image_path"], research)
report = packaging_agent(research, visual["image_path"],
                         copy["quote"], copy["justification"])

The research role may use a tool loop internally. The top-level route remains fixed: research → design → copy → package. The full pipeline preserves intermediate dictionaries alongside the final report path, so each role can be inspected or replaced independently.

07 / Control & communication

Choose who controls the route.

Design questionFixed Python pipelinePlanner-managed team
Who chooses the next role?Application codeA model-produced plan
What varies?Role outputs and internal tool callsSelected roles, order, and possibly repetitions
What stays explicit?Arguments, outputs, tools, and file pathsCapabilities, handoff contracts, execution policy
TradeoffPredictable route; code change needed for a new routeFlexible composition; more paths to evaluate and diagnose

Communication topology is another choice

TopologyShapeQuestion to inspect
LinearResearcher → designer → writerDoes each handoff contain what the next role needs?
HierarchyManager ↔ specialistsWho delegates, reviews, and decides completion?
Deeper hierarchyManager ↔ team leads ↔ specialistsWhere are responsibility and summaries lost?
All-to-allEvery role can communicate with other rolesWhich messages influence which decision?

A planner-managed marketing manager can request research, images, writing, and a review. Roles do not remove the need for execution policy, stopping conditions, or evidence. More communication paths increase the number of handoffs you must understand.

What frameworks package

Underlying mechanismCommon abstraction
Prompt + schema + requestAgent configuration or prompt template
Python function + descriptionTool
Dispatch loop + terminationRunner
Tables + messages + local variablesState or memory
Named return valuesTask outputs and handoffs
Logs + errors + snapshotsTracing or callbacks

These are conceptual mappings, not a LangChain or CrewAI API tutorial. Build and inspect the fixed route first, then experiment with planner selection among the same bounded roles.

08 / Recall & checklist

Explain control, state, and evidence.

Answer before opening the explanation. Then revisit the example that exposed a gap.

Why is the plan an intermediate artifact?

It is a proposal. Application code must interpret it, apply actual controls, execute permitted operations, and inspect results.

What should happen before a multi-item purchase writes?

Validate the complete request, including combined quantities. The original prompt asks for this; stronger application code enforces it.

Why one transaction row per item?

It preserves each line total and the corresponding running-balance transition.

What changes when planning replaces fixed coordination?

The route becomes model-selected. Capabilities, handoff shapes, state access, and execution controls still need explicit ownership.

What does reseed=True do?

Reset demo tables to a known baseline for another experiment.

Why is exec with selected objects not a sandbox?

A Python namespace is not an independent containment mechanism. Reachable objects and builtins can expose broader capabilities.
