A tool is a function plus an interface the model can understand

In the first Module 3 lab, AISuite can translate a Python function and its docstring into a tool definition. The manual version reveals the underlying contract: a tool has a name, a description, and a parameter schema. Those fields help the model decide whether to call it and which arguments to supply.

01

Name

Maps the model’s request to the corresponding local function.

02

Description

Explains when the capability is relevant and what it returns.

03

Parameters

Define the arguments the model must infer from the request.

04

Result

Returns evidence that becomes part of the continuing conversation.

Course design hint: clear, specific docstrings and one responsibility per tool make selection and parameter passing easier to understand.

The tool-use loop alternates model decisions and external execution

  1. 01RequestUser states an outcome
  2. 02Select + bindModel chooses tool and arguments
  3. 03ExecuteFunction runs outside the model
  4. 04Return resultOutput joins the message history
  5. 05Continue or answerCall another tool or summarize

↺ A result can supply the arguments or context required by the next call.

AISuite can manage this cycle automatically when functions and max_turns are supplied. The lab also implements it manually: inspect tool_calls, parse arguments, run the function locally, append the assistant and tool messages, then call the model again.

The first lab grows from one function to multi-tool orchestration

The starting tool, get_current_time(), shows a no-parameter call. The lab then adds weather lookup, text-file writing, and QR-code generation. Given several tools, the model selects the one that fits the request and infers parameters such as file paths, note content, URLs, and image paths.

  1. Time
    Observe the hidden exchange. The model requests get_current_time, receives the local result, and uses the conversation history to answer.
  2. Choice
    Select from a tool set. Weather, note-writing, and QR prompts route to different functions.
  3. Order
    Respect dependencies. In the compound prompt, weather must be fetched before its value can be written into a note, even if the user phrases the tasks in another order.
  4. Trace
    Inspect the full completion. The notebooks print tool calls, arguments, outputs, and the final response so orchestration remains visible.

The email assistant wraps service controls as focused tools

The second lab uses a simulated email backend: FastAPI exposes routes, SQLite and SQLAlchemy store messages, Pydantic validates data, and AISuite tools bridge the model to the service. Endpoint helpers are tested before control is given to the agent.

01Natural-language request“Check unread emails from my boss…”
02AISuite tool layerSearch, fetch, mark, send, delete
03REST serviceFastAPI routes with validated inputs
04Inbox stateSQLite-backed simulated messages

The multi-step example selects search_unread_from_sender, then mark_email_as_read, then send_email. The results of earlier calls provide the context needed by later ones, and the final message summarizes the completed actions.

General explanation: the lab prompt explicitly allows actions without confirmation inside a simulated inbox. In a real service, confirmation and permission rules should reflect the consequence and reversibility of each action.

The registered tool set is the agent’s action boundary

When the email agent is asked to delete a message but delete_email is absent from the registered list, it cannot complete the action. Adding the tool changes the system’s real capability. The “Happy Hour” example then requires the agent to locate the target message and delete it.

Tool missing

The model may reason, but cannot act

No registered function maps the deletion intent to the backend.

Tool present

The agent can search, identify, and delete

The tool list now contains the operation needed to finish the task.

Tool availability is not a menu detail. It defines what the agent can actually do.

Self-check

What are the three core fields in the manual tool schema?

Name, description, and parameters. Together they identify the function, explain its purpose, and specify the arguments it accepts.

Why must weather be fetched before writing the weather note?

The file-writing tool needs the weather value as content, so the weather result is a dependency for the later call.

Why could the first email-agent configuration not delete a message?

delete_email was not registered in the available tool list, so no executable capability matched the requested action.
