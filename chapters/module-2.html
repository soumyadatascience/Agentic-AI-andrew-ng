The reflection loop is a sequence of evidence-producing moves

The course labs implement reflection as a workflow, not as a vague request to “think harder.” An agent creates a first version, runs it, inspects the artifact or result, uses that evidence to revise the work, and runs the revision.

  1. 01Generate V1Draft code or SQL
  2. 02ExecuteCreate observable behavior
  3. 03Inspect outputChart, table, error, or metric
  4. 04Reflect + refineProduce V2 from evidence
  5. 05Execute + validateCheck the claim again

↺ If V2 still misses the goal, its output becomes evidence for the next pass.

A useful separation: generation proposes; execution reveals; reflection interprets; validation decides whether the result is good enough.

Reviewing the artifact is stronger than reviewing the proposal alone

Code can look plausible while producing the wrong meaning. Execution converts a model’s proposal into external feedback: pixels in a chart, rows in a table, an error trace, or another observable result. That evidence can expose failures that are invisible in the text.

Text-only review

“Does this look correct?”

Checks syntax, apparent logic, schema use, formatting, and obvious omissions.

May preserve a plausible but semantically wrong assumption.

Execution-grounded reflection

“Did this produce the right result?”

Checks the proposal against the task and a real output produced in the environment.

Can reveal wrong signs, poor visual choices, missing filters, and broken aggregations.

General explanation: this is a form of feedback grounding. The environment supplies evidence that is independent of the model’s own prose, reducing the risk that the model simply agrees with its first answer.

The chart lab makes the output visible

The first M2 lab asks for a chart comparing Q1 coffee sales in 2024 and 2025. A generation model receives the task and the available dataframe schema, then returns matplotlib code wrapped in <execute_python> tags.

  1. V1
    Generate chart code. The prompt supplies the data columns, the user instruction, and execution constraints such as the output path, required imports, and plt.close().
  2. Run
    Extract and execute the tagged code. The dataframe is available in the execution context, producing chart_v1.png.
  3. See
    Give the chart and original code to a multimodal model. It reviews clarity, accuracy, chart type, labels, color, and readability against the instruction.
  4. V2
    Return structured feedback and refined code. The feedback is parsed from JSON; the revised code is again extracted from execution tags.
  5. Check
    Execute the refined code. The workflow renders chart_v2.png, so the claimed improvement becomes inspectable.
↳

What the image adds: the reviewer can judge the rendered communication—not merely whether the Python seems likely to draw something.

The SQL lab reveals the failure mode text review misses

The second lab asks: “Which color of product has the highest total sales?” Its SQLite table is event-based. Sales record inventory leaving with a negative qty_delta; restocks add inventory with a positive value.

Plausible

V1 query

Uses the schema and groups sales by color. The SQL is valid and looks reasonable.

→
Real output

Negative total

A value such as -190571.46 exposes a semantic error: sales are being summed with the inventory sign.

→
Grounded V2

Correct the sign

The refined query uses ABS(qty_delta) or -qty_delta for sale quantities, then is executed again.

A first reflection function reviews only the question, SQL text, and schema. In the notebook example, that review can confirm the query even though its executed result remains negative. The final approach also supplies the V1 dataframe output to the reviewer. This external feedback gives the model the missing evidence needed to correct the logic.

The key distinction is not “SQL versus charts.” It is proposal review versus outcome review.

Design the loop around artifacts, contracts, and checks

Across both labs, the implementation has the same stable shape even though the artifacts differ.

01

Keep the task visible

Reflection compares the output with the original instruction, not with an abstract standard of quality.

02

Carry forward context

The reviewer receives V1 plus the schema or code needed to explain how the output was produced.

03

Capture external feedback

Pass the rendered chart, dataframe, error, or other execution result into the reflection step.

04

Constrain the interface

Structured JSON, execution tags, explicit libraries, and output paths make responses easier to parse and run.

05

Validate V2

Do not treat revised code as success. Execute it and inspect the new artifact before accepting it.

06

Preserve the trail

Keep V1, feedback, V2, and both outputs so the improvement is observable and debuggable.

General explanation: production systems usually add bounded retries, safety checks before code or SQL execution, timeouts, and explicit stopping criteria. Those are useful extensions; the M2 labs focus on the core generate–execute–reflect–refine sequence.

Recall before you move on

01A first draft is a hypothesis, not a result.
02Execution creates evidence the model cannot get from code text alone.
03Reflection should compare task, proposal, and observed output.
04V2 earns trust only after it is executed and validated.

Self-check

Why could text-only SQL reflection miss the negative-sales bug?

The query was syntactically valid and superficially matched the schema. Only the executed total exposed that negative qty_delta encoded inventory leaving and needed sign correction for a meaningful sales value.

What does the chart image contribute to reflection?

It exposes the actual visual result—chart type, labels, colors, clarity, and readability—so the reviewer can evaluate what a person would see rather than infer it from code.

What is the minimum complete reflection loop in these labs?

Generate V1, execute it, inspect the real output, reflect and produce V2, then execute and validate V2.
