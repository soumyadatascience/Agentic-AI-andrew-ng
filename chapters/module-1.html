Agentic describes a way of organizing work

A single model response maps one input to one output. An agentic workflow can instead plan or select a next step, perform it, observe the result, and use that new information to continue. The value comes from the workflow around the model—not from a label attached to the model itself.

One-shot generation

Prompt → response

Useful when the task is well specified and can be completed in one pass.

Agentic workflow

Goal → steps → feedback

Useful when the task benefits from iteration, external information, or coordinated actions.

General context: applications can range from research and coding to operations and content workflows. The common thread is multi-step progress toward a goal, not a particular user interface.

Autonomy is a dial, not a switch

Systems can differ in how much they decide and act without human input. The right level depends on task risk, reversibility, predictability, and the quality of available checks.

LowAssistantSuggests; a person chooses and acts.
MediumGuided workflowExecutes bounded steps with review gates.
HigherBounded agentSelects and sequences actions within explicit limits.
Decision rule: increase autonomy only when the workflow has enough context, permissions, observability, and evaluation to justify it.

The agentic loop turns a goal into observable progress

  1. 01UnderstandClarify goal and constraints
  2. 02ChooseSelect the next useful step
  3. 03ActGenerate or use a tool
  4. 04ObserveCapture output or feedback
  5. 05EvaluateCompare with the goal
  6. 06Continue or stopRepeat only when useful

↺ Observations update the next decision; a stopping condition keeps the loop bounded.

Benefits such as adaptability, richer task coverage, and reduced manual coordination come from this ability to react to intermediate results. The same loop also creates new responsibilities: decide what the system may do, what evidence it must collect, and when it must stop.

Decompose by dependency, not by arbitrary size

Task decomposition turns a broad goal into steps whose inputs, outputs, and order are clear. A good split makes dependencies visible: later work should receive the evidence it needs from earlier work.

  1. Goal
    Name the desired outcome. Include constraints and what “done” means.
  2. Parts
    Identify distinct responsibilities. Separate information gathering, transformation, action, and checking where useful.
  3. Order
    Connect the dependencies. If one step creates an input for another, make the handoff explicit.
  4. Check
    Place evaluation where errors become visible. Check intermediate artifacts when waiting until the end would hide the source of failure.

Design patterns package recurring workflow decisions

The course outline identifies design patterns as a Module 1 theme. In this learning path, reflection and tool use become the next two concrete modules.

General context: patterns give reusable shapes to recurring workflow needs. They are building blocks to apply when the task calls for them, not goals by themselves.

01

Start from the task

Choose a pattern because it addresses a real bottleneck, not because it is fashionable.

02

Define success early

Evaluation makes the desired behavior observable before the workflow grows complex.

03

Test the whole path

A strong component can still fail when its inputs, handoffs, or stopping rule are weak.

04

Keep control explicit

Bound permissions, steps, and retries to match the consequences of the task.

General context: evaluation may combine deterministic checks, model-based judgments, and human review. The appropriate mix depends on what can be measured reliably and what errors would cost.

Self-check

What makes a workflow agentic rather than one-shot?

It can select or plan steps, act, observe intermediate results, and use those observations to decide what happens next.

Why is autonomy better viewed as a dial?

Different tasks justify different amounts of independent decision-making. Risk, reversibility, predictability, permissions, and evaluation should determine the setting.

Where should evaluation enter a decomposed workflow?

At points where evidence can reveal whether the workflow is still on track—especially after high-risk or dependency-producing steps.
