A tool call is a request to your code.

A model can write “it is 8am,” but it needs a clock to know the current time. A tool lets the application obtain information or perform an operation outside the model.

The model requests a function. Application code executes it and returns the result.

Tools can search, retrieve records, calculate, write a file, send a message, or use another service. A tool call is structured data containing a name and arguments; it is not the operation itself.

Python · the course’s basic tool
from datetime import datetime

def get_current_time():
    """Return the local time of the host running this function."""
    return datetime.now().strftime("%H:%M:%S")

Call the function directly first. Then expose a description so the model can request it. For a question that needs no external information, the model may answer without a tool.

Pause & reason

The model names an unavailable function. Does that create a new capability?

Reveal the reasoning

No. The dispatcher must resolve the name to an available callable. A generated function name is not executable authority.

Separate the model from the service.

The registry maps names to callables. The tool adapter owns service access. The runner owns continuation and the turn limit. Message history carries evidence, but recording a successful-looking message does not independently verify a service mutation.

Follow the request/result exchange.

The manual path has five stages: receive the task, ask the model, dispatch any tool requests, append correlated results, and call the model again. The next call needs the observed output to use it.

Message trace · illustrative Chat-Completions-style encoding
user: "What time is it in New Zealand?"
assistant: tool_calls=[{id: "call_1", name: "get_current_time",
                        arguments: {timezone: "Pacific/Auckland"}}]
tool: tool_call_id="call_1", content="08:00:00"
assistant: "It is 8am in the requested timezone."

Two calls still belong to one assistant response

Append the assistant response once, then append one result for every call ID. Text can accompany tool requests, so the presence of text alone is not a stop condition.

Python · runnable fixture runner
def run(model, max_turns=3):
    messages = [{"role": "user", "content": "What time is it?"}]
    for _ in range(max_turns):
        response = model(messages)
        messages.append(response)  # Once per response, even with two calls.
        calls = response.get("tool_calls", [])
        if calls:
            ids = [call["id"] for call in calls]
            if len(ids) != len(set(ids)):
                return {"status": "invalid_call_ids", "messages": messages}
            for call in calls:
                messages.append({"role": "tool", "tool_call_id": call["id"],
                                 "content": json.dumps(dispatch(call))})
        else:
            return {"status": "complete", "answer": response.get("content", ""),
                    "messages": messages}
    return {"status": "turn_limit", "messages": messages}

This exercise defines its own normalized response contract. It is not a vendor API client. A real adapter must translate provider messages and completion signals, including truncation or other non-successful endings.

Pause & reason

Which history is correct after one response requests two tools?

Reveal the reasoning

User → one assistant response containing both calls → result A → result B → next assistant response. Duplicating the entire assistant response per result corrupts the exchange.

Code execution is a powerful tool.

A calculator with only add, subtract, multiply, and divide cannot answer every new operation. The course instead lets a model write Python, extracts the code between execution tags, runs it, and returns output or an error.

Model output · code as a proposed action
<execute_python>
import math
print(math.sqrt(2))
</execute_python>

The application owns extraction and execution. Errors can feed a reflection pass, connecting this module to external feedback.

Execution boundary: the lesson calls for a sandbox. Passing a restricted-looking dictionary to Python exec is not an isolation guarantee. Treat generated code as untrusted and use an appropriate execution environment with bounded access. Module 5 separates the demo’s actual behavior from stronger engineering controls.

MCP standardizes the connection.

Without a common interface, every application tends to create custom wrappers for every service. The course introduces the Model Context Protocol as a shared client–server connection for tools and data.

The lesson’s comparison is m × n custom integrations versus m clients + n reusable servers. This is an integration mental model, not a literal cost guarantee. Service-specific setup and access control still exist.

The course demonstration connects to a GitHub MCP server to read a README and list pull requests. Retrieved information then becomes context for the model’s response. Protocol compatibility provides connectivity; it does not make every exposed operation appropriate for every request.

What does AISuite derive from a function?

A model-facing description based on the function name, docstring, and parameter information.

Why retrieve weather before writing a weather note?

The writing step needs the actual weather result as input.

What problem does MCP address?

Repeated custom integrations: it supplies a shared client–server interface for capabilities and data.

Where does max_turns belong?

In the runner’s control configuration, separate from tool arguments.

What proves a tool action happened?

A real dispatched operation and observed result, with correlation in the run history—not generated prose alone.
