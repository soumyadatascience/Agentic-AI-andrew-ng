01 / The basic idea

What is an agentic workflow?

Start with a familiar task: write an essay about black holes. You could ask an LLM for the finished essay in one call. Or you could organize several calls around an outline, research, a first draft, and revision.

An agentic workflow is an LLM-based application that completes a task through multiple coordinated steps.

The application carries intermediate results from one step to the next. An outline guides a search; search results inform a draft; feedback guides a revision. The quality of the final result depends on both the model and the workflow around it. Course · p. 4

One task, three approaches

  1. 01 · LLMOutline
  2. 02 · TOOLResearch
  3. 03 · LLMDraft
  4. 04 · LLMReview
  5. 05 · LLMRevise

The five-step version creates a first draft, reviews it, and uses that feedback to revise. Each output becomes an input to later work.

Course example · pp. 21–22. These are workflow designs, not measured results from a live model.

The lesson expands the workflow when the earlier version is not good enough. More steps create opportunities to improve; evaluation tells you whether they actually helped.

Terminology: the course calls its one-pass example “zero-shot.” Zero-shot describes a prompt with no demonstrations; one-pass describes the number of generation steps. Keep these two ideas separate. Module 2 develops prompting examples.

Why use more than one step?

  1. Improve the result

    Research and revision can address weaknesses left by direct generation. The course illustrates this with coding and writing tasks.

  2. Run independent work in parallel

    Separate searches or page downloads can run together before a writing step combines their results.

  3. Replace one component at a time

    Swap a search tool, change a model, or add a checking step without rebuilding the entire application.

Pause & predict

An essay workflow always runs outline → search → draft. Does it need dynamic planning to be agentic?

Reveal the reasoning

No. Under this course’s broad definition, a fixed sequence can be agentic. The application coordinates multiple steps involving an LLM. Dynamic planning is an additional design choice.

02 / Who chooses the next step?

Autonomy is a spectrum.

The useful question is which decisions are written into the application, and which are left to the model? The course uses “agentic” as an adjective so you can discuss this spectrum without arguing over a single definition of “agent.”

DegreeApplication decidesModel decides
Fixed workflowOrder of steps and tool callsContent within each model step
Some autonomyOverall route and available toolsWhich tool or branch to use at selected points
More autonomyAvailable capabilities and execution boundariesTask-specific steps and their order; potentially code for new operations

A fixed invoice process can extract fields and update a database. A customer-service system handling both inventory questions and returns needs different steps for different requests. Visual computer use adds another difficulty: interpreting and acting on a changing interface. Course · pp. 15–19

A useful starting point: choose work with a known procedure, clear steps, and mostly text inputs. Tasks that require planning as you go or interpreting sound and vision are harder to automate.

Several specialized agents can still run in a fixed Python sequence. More roles do not, by themselves, mean more autonomy. Track who chooses the route.

03 / The skill to practice

Break the task into executable steps.

Watch how a person would do the work. Name the actions and decisions. For each step, ask: can a model, a tool, or both complete this? If the answer is no, split it further or add human review. Course · p. 26

Example: respond to a customer email

SJ
Susan JonesSubject: Wrong item shipped

I ordered a blue KitchenPro blender (Order #8847) but received a red toaster instead. I need the blender for my daughter’s birthday party this weekend. Can you help?

“Handle the email” is too broad to be a useful implementation step. Here is a decomposition of the course example:

  1. Extract the request MODEL

    Identify the order ID, expected item, received item, and timing constraint. Return structured fields.

  2. Look up the order TOOL

    Use the order ID to retrieve the actual record. A generated description of an order is not a database lookup.

  3. Draft the reply MODEL

    Use the customer’s request and verified record. Address the issue and urgency without inventing a resolution.

  4. Review the draft HUMAN

    Inspect the draft and evidence. Approve, edit, or reject before the application continues.

Course → practice: page 16 shows a human-reviewed draft; page 23 shows a send step. Our teaching exercise combines these into an explicit review gate followed by a simulated send.

Check the boundary

The model replies, “I updated your order.” What evidence would establish that an update happened?

Reveal the reasoning

A matching application/tool operation and its observed result. Generated text alone does not establish a state change. The execution trace should show which operation ran, with which arguments, and what it returned.

Who owns what?

  • Input adapter: prepares the incoming request and relevant source material.
  • Workflow controller: orders the steps, passes their outputs, and decides when to stop.
  • Model step: reads supplied context and proposes an artifact.
  • Tool or review adapter: performs a specific operation or obtains a review decision.

These are teaching names for responsibilities, not APIs you need to memorize. The same boundaries can exist in a few ordinary functions.

05 / From notes to code

Build a small workflow in Python.

Begin with ordinary functions. This practice file uses fixed fixtures in place of model responses, a local dictionary for order lookup, and a list for the simulated outbox. That lets you examine control flow without an API key.

Teaching extension · the course supplies the workflow idea; this runnable exercise is written for these notes.

Capture a step without losing its input

Python · trace pattern
from copy import deepcopy

def run_step(name, value, function, trace):
    before = deepcopy(value)
    result = function(value)
    trace.append({
        "step": name,
        "input": before,
        "output": deepcopy(result),
    })
    return result

Save the input before executing the step. Copy the output into the trace so a later mutation does not rewrite the recorded evidence. The complete file also captures exceptions and before/after outbox snapshots.

Make rejection change the route

Python · excerpt from the practice file
decision = step("review", draft,
                lambda value: {"approved": approved})

if not decision["approved"]:
    return {"status": "review_rejected",
            "trace": trace, "outbox": outbox}

# Only the approved route reaches the simulated send.
step("send", draft, simulate_send)

A review step has to affect execution. Returning a rejection object and then blindly running the next function would not enforce the decision.

Your turn / a small debugging exercise

What if review is rejected?

Before running the file, predict the step names in the rejected trace. Then inspect the printed approved trace and compare it with run_workflow(approved=False).

  1. Confirm that rejection leaves the outbox empty.
  2. Try an unknown order ID. Confirm that drafting never runs.
  3. Temporarily remove the rejection branch. Run again and identify which assertion catches the bug. Restore the branch afterward.
Expected reasoning

A rejected trace contains extract, lookup, draft, and review. It contains no send. An unknown order stops after lookup. Without the rejection branch, the rejected run reaches send, and its status/outbox checks fail.

Transfer it: choose a real task of your own. Write the one-pass baseline, describe the human procedure, assign executors, define handoff artifacts, then implement the fixed route. Split a weak step or add review where necessary.

06 / Close the learning loop

Measure what the workflow gets wrong.

Build a complete prototype, inspect its outputs, and look for a recurring weakness. Create a focused evaluation to track that weakness while you change the workflow. Start with a small set of examples—roughly 10–20 is a useful development exercise—and expand it as you learn.

Example: unwanted competitor mentions

The course shows customer replies that unnecessarily mention competing companies. This is a concrete behavior you can check with code. Course · pp. 28–29

Python · small objective check
competitors = ["CompCo", "RivalCo"]
replies = [
    "Our team will review your order.",
    "We make returns easier than RivalCo.",
]

def passes_check(reply):
    return not any(name.casefold() in reply.casefold()
                   for name in competitors)

passed = sum(passes_check(reply) for reply in replies)
print(f"{passed}/{len(replies)} replies pass")

Output

1/2 replies pass

This checks listed names using a simple substring match. It is a narrow teaching metric; it cannot establish that a reply is helpful or that every competitor reference is detected.

Evaluation tells you what failed. A trace helps explain where it failed. Inspect the intermediate steps, fix the responsible part, and rerun the same cases. Module 4 develops this process in depth.

Think like an engineer

Every reply passes the competitor check. Have you established that the customer-service workflow works?

Reveal the reasoning

No. You have established one property of those replies. They could still reference the wrong order, omit the deadline, or bypass review. Add checks for important outcomes and inspect failing traces.

07 / Where we go from here

Four patterns to recognize.

These patterns combine the same building blocks in different ways. Learn the mechanism first; a framework can package it later.

Reflection

MODULE 02

Generate, review, and revise. A coding step can use criticism or a failed test to improve its next version.

Tool use

MODULE 03

Request a function and use its result. Search gathers evidence; code calculates; an API performs an operation.

Planning

MODULE 05

Let the model propose task-specific steps and their order, including which available capabilities to use.

Multi-agent collaboration

MODULE 05

Give specialized roles separate responsibilities and explicit handoffs—for example, a coder and a critic.

Reflection and tool use fit inside fixed workflows. Planning introduces decisions about the route itself. Multi-agent collaboration can use either a fixed route or dynamic coordination.

08 / Close the notes first

Can you reconstruct the idea?

Try answering aloud or on a blank page before opening each explanation.

How does the course define an agentic workflow?

An LLM-based application that completes a task through multiple coordinated steps. The route can be predetermined or more dynamic.

What are the two basic kinds of building blocks?

Models and tools. Models generate, interpret, or decide. Tools connect the application to APIs, retrieval, databases, and code execution. Human review supplies a deliberate handoff when needed.

What should you do when one step performs poorly?

Inspect the step, compare it with the human procedure, and consider splitting it into smaller executable steps or adding human review. Measure the change using the same cases.

Draw the email workflow and label every artifact.

Email → extracted request → retrieved order → draft → review decision → simulated receipt if approved. The application owns sequencing and the branch after review. The trace preserves intermediate evidence.

Why does the trace copy the input before execution?

The step may replace or mutate its input. A snapshot preserves what actually entered that step instead of accidentally recording the later value.

How would you know if adding a review pass helped?

Compare results with and without that pass on the same evaluation cases. Extra steps alone do not prove better quality.
