Give the draft a second pass.

Suppose you ask a model to write an email. The first draft may omit a date, sound abrupt, or contain a typo. A second call can inspect those specific issues and produce a revised draft.

Reflection is a designed generate → review → revise workflow.

The application schedules the review. The model does not need to invent the workflow or decide whether to reflect. You can use the same model for generation and review, or choose a different reviewer.

  1. Generate V1

    Create a concrete candidate: text, code, SQL, or a chart.

  2. Review against criteria

    Inspect the candidate for the properties the task requires.

  3. Produce V2

    Use the feedback to revise, then check the revised result.

Prompting vocabulary: zero-shot means no demonstrations; one-shot means one demonstration; few-shot means several. These describe examples inside a prompt. Reflection adds a separate review/revision stage.

Where does feedback enter?

The controller repeats the execution boundary for V2 and retains both versions. The reviewer proposes changes; application code executes them. A framework may package this sequence, but it still needs explicit inputs, outputs, and stopping rules.

A query can run and still be wrong.

The SQL lab asks which product color has the highest total sales. Sales decrease inventory, so their qty_delta is negative. Treating this value directly as revenue gives a plausible query the wrong meaning.

A tiny fixture you can check by hand

For this example, “sales” means gross revenue from sale events, excluding returns and restocking. Blue has 3 × $20 = $60; red has 1 × $20 = $20.

ColorActionQuantity deltaUnit price
bluesale−3$20
redsale−1$20
redrestock+10$20
SQL · V1
SELECT color, SUM(qty_delta * price) AS revenue
FROM events WHERE action = 'sale'
GROUP BY color ORDER BY revenue DESC LIMIT 1;

Observed V1

red | -20

Descending order picks −20 ahead of −60. The query executes successfully but selects the wrong top-selling color. The revised query uses SUM(-qty_delta * price) on sale events.

Observed V2

blue | 60

The course’s external-feedback path supplies the actual result dataframe as df_feedback. The reviewer can inspect question, schema, original query, and returned rows before producing feedback and V2.

Do not generalize the sign fix blindly. Taking absolute values of every event would count restocks as sales. First define the business metric and filter the relevant actions. Negative values are evidence to investigate, not a universal proof of an error.

Does reflection earn its extra call?

Compare direct generation and reflection on the same examples. Objective tasks can have known answers. Subjective artifacts need an explicit rubric.

TaskEvaluationWhat to preserve
SQL answerCompare with expected resultQuestion, data, V1/V2 queries and rows
ChartScore title, labels, type, and rangesImages, code, feedback, criterion scores
Runtime behaviorCheck parse and execution failuresRaw model response, exceptions, artifact paths

The course warns about position bias in direct A-versus-B judgments. Rubric-based scoring gives the judge explicit dimensions instead of relying on an unconstrained preference. A rubric still needs checking against human judgment.
