A plausible answer is not an operational workflow

A direct model call can describe what should happen. The moment the request touches inventory, transactions, files, or another agent, description is no longer enough.

Consider the customer question, “Do you have any round sunglasses in stock that are under $100?” A model can produce a fluent sentence from its own language ability, but the store needs an answer grounded in live records. It must interpret round as a product constraint, read current stock, apply a price ceiling, and return a short response. For a purchase or return, the stakes rise: the workflow must also preserve inventory and transaction consistency.

The application therefore cannot hand ownership of the operation to a single generated paragraph. It needs a route from intent to evidence. The course introduces planning as the mechanism that proposes this route at runtime. In the code-execution lab, the plan is Python: comments explain the steps, executable statements perform them, and named outputs expose the result.

Separate capability from authority. The LLM is capable of composing filters, calculations, and updates. The executor determines which objects and helpers the generated code can reach. The state tables remain the operational source of truth.

This separation is the durable engineering lesson. The model can choose a request-specific sequence without the application pretending the sequence is safe merely because it was generated confidently.

A plan is an intermediate artifact, not magical autonomy

In a fixed workflow, the developer decides the order of operations before the request arrives. In a planning workflow, the model receives the goal, data description, available helpers, and policy, then writes a route for the current request. That route may be a structured list of tool calls or executable code. Either way, it is produced between the request and the effects.

Calling the plan an artifact matters because artifacts can be extracted, checked, logged, rejected, executed, and compared with results. A plan is not yet a state change. It is a proposal encoded in a form the rest of the application can process.

The lab prompt makes the proposal more disciplined. It tells the model to derive every constraint from user_request, build TinyDB queries dynamically, default ambiguous intent to a read-only dry run, and always set answer_text plus a defined STATUS. It also declares a transaction policy before generation: validate the whole request before writing, create one transaction row per item, and update the running balance sequentially.

These are not implementation trivia. They define the behavioral envelope inside which the plan may vary.

Three functions make the control model legible

The useful abstraction is not “an agent object.” It is a small set of functions with explicit callers, inputs, effects, and returns.

The signatures below normalize the notebook into teaching contracts. Names such as extract_tagged_python and validate_plan make hidden responsibilities visible; they are explanatory helpers, not claims about extra verbatim notebook functions.

The policy must be visible before execution

  1. 01
    Derive constraints from the request.

    Shapes, keywords, price ranges, quantities, stock requirements, and action intent come from user_request; the plan should not smuggle in fixed values.

  2. 02
    Ambiguity means read-only.

    If the intent to buy, return, restock, or adjust is not clear, the workflow performs a dry run instead of changing state.

  3. 03
    Validate the whole request first.

    For a multi-item purchase, confirm that every item exists and has sufficient stock before mutating anything.

  4. 04
    Preserve per-item accounting.

    Each item gets its own transaction row. The next balance begins from the preceding row’s balance.

  5. 05
    Always produce a human answer and machine status.

    answer_text stays short; STATUS is one of success, no match, insufficient stock, invalid request, or unsupported intent.

Failure paths are state transitions too—even when state does not change

If the request asks for more units than are available, the workflow returns insufficient_stock, states the available quantity, and performs no writes. If a required quantity cannot be parsed, the status is invalid_request. If the action is outside the store’s supported capabilities, the status is unsupported_intent. If no product matches, the status is no_match and the answer offers a nearby alternative or next step.

reseed=True does not grant extra authority and is not part of the customer’s intent. It is a reproducibility control for the demonstration: reset the inventory and transactions to a known baseline so repeated experiments are comparable. With reseed=False, later calls continue from prior state.

The trace—not only the answer—is the engineering artifact

“Great, I’ve reserved…” is useful to the customer. It is insufficient for the engineer who must understand whether the reservation was correct.

The answer compresses the workflow into one sentence. The trace retains the distinctions that make the system inspectable: the original question, the generated code, the stdout log, any exception, the explicit status, and the before/after tables. From those artifacts, a reviewer can ask whether the plan parsed the right quantities, checked all items before writing, used one transaction per item, and advanced the balance in the correct order.

This is also why generation and execution should remain separate. If the generated plan is wrong, inspect the prompt, schema, and plan. If the plan is sound but execution fails, inspect extraction, approved objects, runtime error, and state snapshots. If the final answer is wrong even though the state is right, inspect result packaging. Each boundary narrows the place where an error can live.

A short response and a rich trace serve different audiences. Keep technical details in artifacts and logs; keep answer_text customer-friendly. Do not force one representation to do both jobs.

The same artifact discipline scales to a small team

The market-research lab changes the domain but keeps the architectural idea. Instead of one code plan touching store state, a fixed Python pipeline moves increasingly refined artifacts through four specialized roles. Each agent has a narrower responsibility, and each handoff becomes an inspectable input to the next step.

Each role owns one transformation

The Market Research Agent loops through tool calls until the model returns a final summary. Its output is a trend brief that includes leading trends, matching catalog products, and justification. The Graphic Designer Agent turns that text into a JSON-shaped prompt and caption, sends the prompt to an image model, saves the image locally, and returns {image_path, prompt, caption}.

The Copywriter Agent receives two artifacts: the local image and the trend summary. It returns a short quote plus a justification. The Packaging Agent receives the summary, image path, quote, and justification; it asks the model to rewrite the summary for an executive audience, then writes the final Markdown report and returns its path.

The full pipeline function is deliberately unsurprising. It calls research, then design, then copywriting, then packaging, storing each return value in a named variable. Its final dictionary keeps the trend summary, visual result, quote result, and Markdown path. That explicitness is the point: every handoff can be viewed, tested, or replaced independently.

Fixed orchestration and planner-managed coordination move the control point

A fixed multi-agent pipeline and a planner-managed team can contain the same roles. What changes is who decides the next step. In the lab pipeline, Python determines the sequence before runtime. In the course’s planning example, a marketing-manager model receives descriptions of the available agents and proposes which one to call, in what order, and when to review the result.

The course also shows that communication topology is a separate decision. A linear chain passes work in one direction. A hierarchy places a manager above specialist agents. A deeper hierarchy lets sub-agents coordinate teams of their own. An all-to-all pattern permits direct communication among every role. Greater flexibility changes the debugging burden because more paths can carry context and feedback.

The framework labels are conceptual mappings of the course’s taught building blocks, not a framework API tutorial. The underlying design questions remain: who owns control, which state is visible, what may mutate, and which artifacts cross each boundary?

A practical design checklist

  1. Name the state.

    List every table, message history, file, and intermediate result the workflow can read.

  2. Mark mutation authority.

    For each function, state whether it can write and which preconditions must hold first.

  3. Separate generation from execution.

    Return the plan before running it so the proposal remains inspectable.

  4. Define the plan envelope.

    Declare available helpers, output tags or fields, allowed statuses, and response requirements.

  5. Validate before the first write.

    For multi-item work, check the full request so partial mutation does not precede a predictable failure.

  6. Make handoffs concrete.

    Use named artifacts—summary, image path, prompt, caption, quote, justification, report path—instead of vague shared context.

  7. Return evidence with the answer.

    Preserve status, stdout, errors, and before/after state for review.

  8. Control reproducibility explicitly.

    Treat reseeding as a test setup choice, never as inferred business intent.

Durable takeaways

Plans are data before they are effects.

Capture and inspect them at the boundary.

Expressiveness increases the need for containment.

Code can compose rich operations, so its accessible runtime must be explicit.

State policy belongs in the contract.

All-items validation and sequential balance updates are correctness rules, not stylistic preferences.

Handoffs are the multi-agent architecture.

Roles become a system only when their artifacts and order are defined.

Try it in code

  1. Seed a tiny inventory table and a transaction table with one opening-balance row.

  3. Implement generate_llm_code(...) and verify it cannot mutate state.
  4. Add extract_tagged_python(...), then test empty, tagged, and raw-code inputs.
  5. Write a visible validate_plan(...) policy gate before execution.
  6. Implement execute_generated_code(...) with approved objects, stdout capture, errors, status, and snapshots.
  7. Test a read-only query, a return, a valid two-item purchase, an insufficient-stock purchase, and an ambiguous request.
  8. Build four plain Python functions for research, design, copywriting, and packaging; pass named dictionaries between them.
  9. Only after the fixed pipeline is observable, experiment with a planner choosing among the same bounded roles.

Self-check

Why is the plan an intermediate artifact rather than the final authority?

Because it is a model-produced proposal. Application code still extracts it, applies policy, supplies approved runtime objects, observes effects, and packages results.

What must happen before a multi-item purchase mutates inventory?

Every requested item must be identified and checked for sufficient stock. If any line fails, the workflow returns an appropriate status and performs no mutation.

Why create separate transaction rows for separate items?

Each line total gets its own record, and the running balance advances sequentially from one transaction to the next.

What changes when coordination moves from Python into a planner?

The route—selected roles and their order—becomes dynamic. Agent capabilities, handoff contracts, execution policy, state access, and result capture still remain application-defined.

What does reseed=True mean?

Reset the demonstration data to a known baseline for a clean, reproducible run. It is not a customer action or a relaxation of mutation policy.
