Prototype first, then turn observed failures into evals

The lessons recommend a fast, rough end-to-end prototype. Manually inspect roughly 10–20 outputs, find a recurring problem that matters, and build a small test set that measures it. The eval can grow as the system matures.

An evaluation system sits beside the product workflow

The agent produces outputs for users. The development system preserves inputs, outputs, traces, labels, scores, and failure categories so the team can decide what to change next.

Module 4 turns evaluation from a final report into a development control loop. The workflow is built end to end first. A small set of examples reveals an important error mode. An evaluator measures that behavior repeatedly while prompts, models, tools, or algorithms change. Error analysis then uses traces to assign failures to components, and component-level evals make repeated optimization faster and less noisy.

The product path and the evaluation path share run artifacts but have different responsibilities. Production components answer the task. Evaluators compare results with ground truth, shared rules, gold-standard talking points, or a rubric. Error analysis does not generate a new answer; it turns poor runs into a distribution of causes. The improvement step changes one component, then both component and end-to-end measures are rerun.

Error analysis turns traces into priorities

A trace contains the workflow’s intermediate outputs; an individual step is often called a span. Read the traces for cases with poor final results, judge which steps fall short of what a capable person would produce from the same input, and count the frequency of each failure source.

  1. Filter
    Study the failed cases. Correct cases contribute less information about what to fix next.
  2. Trace
    Inspect each step. In a research workflow, check query generation, returned pages, and source selection separately.
  3. Label
    Name the component at fault. An invoice error may begin in PDF-to-text or in the LLM extraction step.
  4. Count
    Quantify failure frequency. Work first on the component responsible for the largest share of important errors.

Framework-free evals are data, scorers, and aggregation

The following Python-like contracts are teaching decompositions of the course examples. They make visible what an evaluation library would package: test cases, a runner, one or more scorers, and a summary that remains comparable across workflow versions.

def evaluate(workflow, cases, scorers):
    runs = []
    for case in cases:
        result = workflow(case.input)
        scores = {
            scorer.name: scorer(case, result)
            for scorer in scorers
        }
        runs.append({
            "case_id": case.id,
            "result": result.answer,
            "trace": result.trace,
            "scores": scores,
        })
    return aggregate(runs)

def exact_due_date(case, result):
    extracted = parse_yyyy_mm_dd(result.answer)
    return extracted == case.expected_date

def rubric_judge(case, result, rubric):
    response = judge_model(case.input, result.answer, rubric)
    return parse_criterion_scores(response)

def attribute_failures(failed_runs, component_names):
    counts = {name: 0 for name in component_names}
    for run in failed_runs:
        cause = inspect_trace_and_label(run.trace)
        counts[cause] += 1
    return sort_descending(counts)

evaluate does not decide whether a metric is meaningful; the developer chooses scorers based on observed failures. exact_due_date demonstrates objective comparison with per-example ground truth. rubric_judge demonstrates structured subjective grading. attribute_failures represents the manual error-analysis table: inspect poor examples, label the component that failed, then count categories.

Evaluation failure modes

Metric blindness

The score misses a problem a human sees.

Improve the metric, not only the workflow.

Noisy end-to-end signal

Later stochastic steps hide a small improvement in the component under test.

Add a component-level eval.

Judge inconsistency

A vague comparison or position bias changes the verdict.

Use criterion-level rubrics and structured output.

Unrepresentative set

A tiny test set contains only easy cases.

Add examples from observed failures.

Optimization drift

A component metric improves while user-facing quality worsens.

Rerun the end-to-end eval.

Component-level evals produce a clearer, cheaper signal

Rerunning an entire search–draft–reflection workflow after a small search change is expensive and noisy. Later stochastic steps can hide a modest improvement in the component being tuned.

The Module 4 lab makes the research step independently testable with find_references. It extracts returned URLs, checks them against a preferred-domain list, computes the preferred-source ratio, and returns a pass/fail result plus a Markdown summary.

Turn one failure into an instrument.

Create a small error ledger from printed traces, count failures by component, then implement the matching focused evaluator. Change one component decision and rerun the same metric before returning to the end-to-end score.

The course does not claim that every research failure begins in search. The point is procedural: inspect the actual trace and count evidence before choosing a fix. Another case may expose poor source selection or weak reasoning over fetched text. Invoice traces similarly separate PDF-to-text errors from LLM date-selection errors. Email traces separate query drafting, database behavior, and response tone.

Try it in code

  1. Collect 10-20 representative tasks and store the expected field, rule, talking points, or rubric beside each input.
  2. Run the complete workflow and retain final outputs plus span traces.
  3. Implement the cheapest objective scorer that captures one important failure.
  4. For subjective quality, request criterion-level JSON rather than a single preference.
  5. Filter failed cases, inspect traces, and label the first component where the run became unsatisfactory.
  6. Count failure categories and choose the highest-impact component.
  7. Build a focused component eval, change one parameter or implementation, and rerun it.
  8. Rerun the end-to-end eval before accepting the change.
  9. Once quality is adequate, measure every span's latency and cost contribution before optimizing.

Different components require different interventions

Non-LLM component

Tune or replace it

Adjust search result count or date range, retrieval thresholds or chunk size, and model thresholds—or compare a different service.

LLM component

Change input or structure

Clarify the prompt, add examples, compare models with the eval, or split a difficult step into generation and reflection.

The lesson places fine-tuning last: consider it only after prompt changes, model comparison, and task decomposition have not delivered the needed improvement.

Build model intuition deliberately: try multiple models on a personal evaluation set and read effective prompts for ideas about how to use them. Then choose the application model with the evaluation rather than intuition alone.

Benchmark latency and cost only after output quality works

The course orders the priorities deliberately: make the system useful first, then optimize latency, and focus on cost when scale makes it important.

Self-check

Why begin with 10–20 examples?

A small set is enough to establish a useful signal quickly; it can expand as the workflow and evaluation mature.

Why can a component eval be clearer than an end-to-end eval?

It isolates the changed step, avoids the cost of the full workflow, and reduces noise introduced by later components.

When should latency and cost become the main optimization target?

After output quality meets the application’s needs; cost becomes a priority when usage makes it materially important.
